01 · Business view

Conceptual model

The conceptual model describes the business objects and how employees use them. It avoids implementation details such as table names and column types.

Relationship labels use larger, high-contrast text and opaque badges so they remain legible over connectors. The model distinguishes Shareholder records from employee identities and pending requests from completed ledger movements.

People and ownership

A Shareholder has a profile, family-line details, and one or more share certificates. A certificate identifies a class and numbered issue; remaining shares are calculated from its issued and transferred quantities.

Requests and completed events

Issuance and transfer requests collect the details and approvals. Approval does not itself move shares. A completed transfer records the ledger movement and links to the resulting certificate.

Employees and signers

Employee sign-in identity is separate from Shareholder identity. Named Settings signers approve actions when their configured email matches the employee’s verified account.

Documents and history

Certificate PDFs and uploaded files are represented in the database by object references and metadata. Activity and settings-audit records describe who changed information and when.

02 · Database view

Logical model

The logical model maps those concepts to the PostgreSQL entities implemented in the application. PK marks a primary key; FK marks an enforced foreign key; UQ marks a unique value. Fields below are grouped for readability; names shown are database column names.

Logical Data Model Summary

This page-sized overview replaces the detailed diagram in this document. It shows all 18 tables, primary-key and foreign-key columns, and enforced relationships only; use the independent summary SVG for lossless zoom. The full-column diagram is retained separately as Logical Data Model Detailed. The descriptive data dictionary below is retained for reference.

Additional uniqueness rules: certificate class + sequence number; one active template per share class; one completed PDF per certificate and per request; approval-request email per request + signer; outcome email per request. CHECK constraints limit classes, statuses, quantities, and request payload kinds. These rules supplement the key-only summary; column-level uniqueness markers remain in the separate detailed model.

Important distinction: the schema is partly relational and partly JSONB. Shareholder profile details, approval snapshots, batched source certificates, and some request inputs are stored as JSONB rather than as one column or join table per field.

03 · Interpretation

Key rules & boundaries

  • Holdings are calculated from certificates. There is no separate share-balance table; issued quantity and transferred quantity drive certificate balances and shareholder holdings.
  • Family line is not a separate entity. Family line and generation number are profile attributes in the shareholder JSONB record.
  • Batch inputs are embedded records. A completed transfer stores its list of source certificate IDs and quantities in share_transfers.sources; there is no normalized transfer-source junction table in the current schema.
  • Approval evidence is captured per request. required_signers and approvals are JSONB snapshots. The Settings signer roster is maintained separately in signoffs.
  • Legacy fields are not current approval policy. Older CEO/CFO columns remain on transfer_requests for compatibility; the current workflow is driven by Settings-configured signers.
  • Stored files are external to PostgreSQL. Database rows retain object paths and metadata; the PDF, image, or attachment bytes live in object storage.
  • Access is employee-side in Phase 1. The database has no shareholder self-service account relationship or shareholder editing workflow in this phase.
Privacy note: SSNs are stored separately from the flexible shareholder profile and encrypted at rest by the application. This model intentionally contains no real people’s names, emails, SSNs, or holdings.
