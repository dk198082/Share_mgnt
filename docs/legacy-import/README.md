# Legacy import — mapping and conversion review

**Status:** Mapping reference plus an authorized [Preview sample utility](preview-utility.md) and [Azure import access for every signed-in app user](azure-import-setup.md). Live Azure verification, production reset and real-data import remain separate, unapproved execution work under the [saved plan](../legacy-data-import-plan.md).

## Current review approach

Use the simplified [destination-first table/field mapping](destination-first-mapping.md) for business review. The main workbook has three mapping tabs: **Shareholders**, **Certificates**, and **Share_Transfers**, with required/optional guidance, proposed sources and review columns. Individual shareholder profile fields are included on Shareholders. **Other Tables** summarizes the remaining 15 tables as configured, generated or not imported; the full 18-table/162-column reference remains in the companion document for technical use. A small representative sample is sufficient for design and development; a complete anonymized dataset is **not** requested. Full real-data reconciliation happens later in the approved Azure environment.

## What has and has not been built

Prepared a source assessment, source-column disposition register, proposed field mappings, conversion rules, blank Excel templates, and a wholly synthetic example workbook. The files are generated by `scripts/legacy_import_review/build_review.py`.

Following the review, the user authorized building the utility and confirmed the six new files are anonymized, with Replit Preview as the seed target. A Settings screen, profile-scoped converter, staging/commit API and persistent run history are now implemented. The matching sample profiles/certificates were added without replacing existing records. Real-data importing is blocked on Replit. In a correctly configured Azure deployment, every signed-in app user can use the utility without additional permissions. No reset command, real-data import, SharePoint file import or production cutover was performed. Review-package generation remains offline; runtime verification uses a separate owned database cluster with wholly synthetic fixtures.

The supplied files are treated as user-described anonymized design examples, not authoritative migration input. Several contain export-author names/emails in report headings. The raw workbook also retains substantially more security rows than profile rows. Do not assume every worksheet or export header was scrubbed. Generated examples contain none of those source-row values. Before sharing further examples, check all sheets, metadata, comments, and headers.

## Review these first

1. **Fractional shares are required for both Common and Preferred, with up to two decimal places.** This applies to issuance, full/partial/batch transfers, allocations, balances, approvals, reports, certificate PDFs and imports, including `0.01` shares. Runtime support is implemented separately from the importer; Azure requires the reviewed quantity-column migration before fractional production writes. Reject excess precision rather than rounding or truncating. Certificate sequence numbers remain whole numbers. A complete anonymized dataset is not required for design.
2. **The examples are not a complete linked dataset.** Raw `Securities` has 581 rows referring to 144 distinct owner IDs; `StakeholderCompanies` contains one profile. Consequently 575 security rows lack an owner profile in this sample. The separate shareholder report has two profiles, while the detailed cap table has five Common certificates and one Preferred certificate for one holder. This is an expected possibility with reduced samples, not proof the original system is broken. A synthetic, internally linked subset or complete approved Azure-side exports will be needed for end-to-end reconciliation.
3. **Do not select totals by filename.** The custom share-class report shows 75,206 Common fully diluted shares; the raw class/security records and cap-table summary show 75,200. The six-share difference requires reconciliation of definition, snapshot, filters, and coverage. These are source evidence values, not approved import balances. Reduced ownership totals cannot be compared with unreduced company totals.
4. **Certificate uniqueness needs review.** The raw file has one repeated certificate-number group. Do not merge or renumber it automatically. Determine whether it is a duplicate export row, legacy numbering exception, or distinct security requiring an approved application change. Retain the separate raw security IDs while resolving it.
5. **History is possible but not yet proven complete.** There are 105 nonzero `TransferredFrom` references, all resolving to raw security IDs within the supplied securities sheet. That is useful evidence, but it is not a transfer transaction log. It does not itself establish all source allocations, exact transfer dates, reasons, historical actors, or PDF links. No historical transfer row is approved from that evidence alone.
6. **Cancellation has ambiguous meaning.** Some raw `TRANSFERRED` securities also carry `CancelledAmount` and `CancellationReason=TRANSFER`. That value must not be counted again as a true cancellation. Pulley `AcceptanceStatus=PENDING` is not an app sign-off request; it must never create pending approvals.
7. **Personal/history fields and files are incomplete.** These layouts do not supply date of birth, date of passing, phone, a dedicated family-line field, or historical employee attribution. The user has approved `Stakeholders.Comments` as the Family line source; preserve that text and retain it in notes. Termination date is not date of passing. No actual certificate PDFs or document manifest were supplied.
8. **Current document storage needs an import-aware design.** `certificate_documents` requires live approval-request and template references. Historical PDFs cannot be inserted there honestly by inventing approvals or attributing present-day signatures. Propose import provenance and a legacy-document path, with visibility in shareholder history and Transfer History, before implementing historical PDF loading.

## Proposed source roles

Use matching schema/header signatures, not uploaded filenames alone, to recognize exports. Every staged row must retain source file fingerprint, sheet, physical row number, source system and mapping revision.

| Source | Proposed use | Important limit |
|---|---|---|
| Raw cap table — `StakeholderCompanies` | Technical shareholder ID and structured identity crosswalk | One example profile; no assumption that External ID is a unique technical key |
| Shareholder report — `Stakeholders` | Personal/contact fields, external business ID, comments; enrich only after a reviewed ID link | Name/email are not relationship keys; conflicting contact values require review |
| Raw cap table — `Securities` | Primary candidate certificate/security ledger and parent-link evidence | Fractional amounts, duplicate certificate number, missing owners, transfer semantics unresolved |
| Raw cap table — `ShareClasses` | Resolve class IDs to Common/Preferred; class controls | Legal rights, par value, liquidation terms and authorization are not automatically adopted |
| Detailed cap table — `C-Common`, `PS-Preferred` | Certificate-level cross-checks; textual vesting and financial/history evidence | Reduced sample; some movement columns summarize rather than enumerate transactions |
| Detailed cap table — `Summary`, `Ownership`, `Voting Ownership` | Reconciliation controls for the same snapshot and population | Do not create certificates from aggregate totals |
| Standalone ownership report | Independent holder/class balance cross-check | Same totals appearing in several reports are not additive |
| Securities granted report | Issuance date/quantity/class cross-check | Not a substitute for a full transfer ledger; report only contains a subset |
| Grants outstanding/cancel report | Review cancellation dates, reasons, and quantities | Confirm whether amounts represent transfers, expiry, cancellation, or repurchase |
| Vesting report — three sheets | Supplement schedule descriptions; retain vesting evidence | Event and milestone sheets have headers but no example event rows |
| Custom share-class and shareholder contribution reports | Class/holder totals and contribution reconciliation | Do not create financial rights or overwrite current Settings prices |
| Raw `Company`, `Convertibles`, `EquityPlan` | Company controls; inventory unsupported instruments | Convertibles and EquityPlan contain no example rows; no support is implied |

The Excel **Source Columns** register lists every discovered header with a disposition. “Archive / review” means preserve in an approved Azure/SharePoint legacy archive, not silently discard or write an arbitrary JSON property into the app.

## Proposed normalized templates

Prefer direct Pulley exports once their adapters are approved. Templates provide a fallback, a clear contract for missing information, and future controlled imports; employees should not have to rekey all exports.

| Sheet | Key | Purpose |
|---|---|---|
| Import_Run | run_reference | Source/cutoff/scope/mapping reference; review evidence, not executable approval |
| Shareholders | legacy_shareholder_id | Personal and business fields; distinct from app-generated ID |
| Identity_Links | source_report + source_row_reference | Reviewed links from report rows to raw shareholder IDs |
| Certificates | legacy_security_id; certificate_id also unique | Original and ending balances, class, status and legacy evidence |
| Transfers | legacy_transfer_id | Reviewed historical movements with source and recipient owners |
| Transfer_Allocations | legacy_transfer_id + source_certificate_id | One or many source certificates, one recipient certificate |
| Documents | legacy_document_id | Manifest linking original files to legacy entities |
| Reconciliation | scope + owner/class | Approved controls for matching scope/cutoff |

Every template column has required/conditional guidance, a destination or explicit gap, formatting instructions, and a source reference in **Field Definitions**. Empty cells mean unknown/not supplied, not zero. Blank templates have no example records. Examples are in a separate file.

Decimal quantities are **text in the design templates**, with up to two decimal places for both classes. Reject excess precision rather than rounding. The ordinary synthetic example uses whole shares; fractional runtime behavior is verified separately by the isolated suite documented in `docs/two-decimal-share-quantities.md`. The importer remains unimplemented.

## Conversion and validation rules

### Identity and personal information

- **R01 — Separate identifiers.** Keep Pulley technical shareholder/security IDs as text in a durable source-to-app crosswalk. Proposed key: `(source_system, entity_type, legacy_id)` unique across runs. App IDs are assigned once on first approved promotion and reused on retries. `External ID` maps to `shareholders.data.generationNumber`, not to a technical FK. Preserve zeros and alphanumeric business IDs; do not require a numeric generation.
- **R02 — No fuzzy linking.** Use technical IDs where present. Resolve report-only rows through a reviewed identity link. A unique External ID may be suggested as evidence, never assumed globally unique. Duplicate names/emails/external IDs require review; names/emails must not silently merge people.
- **R03 — Contact conflicts.** Trim outer whitespace, preserve meaningful internal text and name case. Validate emails; do not require email for deceased/legacy holders. Assemble nonblank street/city/state/postal/country components in a documented display order, retaining components in staging. Do not overwrite conflicting values using workbook order.
- **R04 — Missing and protected information.** Missing birth/passing/phone values stay blank. Map Family line from `Stakeholders.Comments` as approved by the user; blank Comments means blank Family line. Reject text over 200 characters rather than truncate. Never infer personal dates or family lines from names, termination or share activity. Keep SSNs blank in synthetic examples. On Azure, a separately approved protected path would normalize nine digits, encrypt with the app-compatible mechanism, show only masked values, and prohibit plaintext in receipts, error files, activity diffs and logs. Masked SSNs do not reconstruct missing digits.
- **R05 — Type and comments.** Preserve shareholder type/relationship/termination as legacy evidence pending dedicated destination approval. Do not treat a treasury/entity name as a human or infer death. Proposed mapping for Comments is `financialNotes` (the app's section 04 notes field); obtain business approval, preserve the original separately, and enforce the app's 5,000-character limit rather than truncate.

### Certificates, quantities and history

- **R06 — Class and certificate numbers.** Resolve `SecurityClassId` through raw `ShareClasses.Id`, require approved names Common or Preferred, and verify matching `C-`/`P-` prefixes and positive numeric suffixes. `PS-Preferred` is a sheet title, not permission to change `P-` certificate IDs. Flag leading-zero or other legacy formatting that would violate the current exact ID constraint; do not renumber silently.
- **R07 — Precision.** Both Common and Preferred support up to two decimal places, including positive quantities below one share. Use exact hundredth-share arithmetic throughout storage, APIs, forms, issuance, transfers, batch allocations, approvals, holdings, reports, certificate PDFs and imports. Reject excess precision, malformed values, prohibited negatives and scientific notation in templates; never round or truncate. Original quantity must be positive; the existing per-operation ceiling is 1,000,000,000,000 shares. Certificate numbering remains integer-based. Azure quantity-column migration/release is separate from importer review or execution. Historical money retains its own precision and is optional; blank is not zero.
- **R08 — Balance and status.** Require original = outstanding + verified transfers-out + genuine cancellations + genuine repurchases (and any separately approved movement categories). Do not derive transferred quantity from original minus outstanding when cancellations/repurchases are ambiguous. Candidate translations: OUTSTANDING with no depletion -> Outstanding; OUTSTANDING with proven partial transfers -> Partially Transferred; TRANSFERRED with zero outstanding and fully evidenced depletion -> Transferred; CANCELLED with genuine cancellation evidence -> Cancelled. Mixed/unsupported depletion blocks promotion. The current model has no separate cancellation/repurchase quantity ledger; do not encode these as transfers.
- **R09 — Acceptance is not approval.** Preserve Pulley acceptance state as legacy evidence. Never create app approvals, signers, notifications or pending sign-off requests from that state.
- **R10 — Historical links.** Treat `TransferredFrom` as a candidate parent security-ID link, not as a transfer ID or proven allocation. Require no self-links/cycles, resolved IDs, same class, different source/recipient owners for supported transfer flows, chronological consistency, and approved date/quantity evidence. Cancellation dates or recipient issue dates are candidate transfer dates only if business rules explicitly approve their meaning. Preserve source date/time precision; do not invent timestamps.
- **R11 — Batches.** Each historical transfer has one source shareholder, one recipient, one class and one recipient certificate. Allocations reference distinct source certificates owned by the source, sum exactly to transfer quantity and cannot exceed availability at that historical time. Multiple owners/classes in a source set are unsupported. Do not replay movement services or issue a replacement certificate to import history.
- **R12 — History scope.** Full history requires reconciled historical certificates, movements and allocations. If evidence is insufficient, propose opening balances at the approved cutoff plus a clearly labeled legacy archive. Do not set “transferred” just to make an opening balance match or present an incomplete history as complete. Any representation of original versus opening quantity and canceled/repurchased positions requires explicit approval.
- **R13 — Attribution and counters.** Retain a known historical actor/time only when supplied. Unknown historical actor remains unknown; the import employee/time is separate provenance, not historical authorship or approval. Preserve certificate IDs and set each class counter above its highest imported/retained reserved number only during approved promotion. Never derive a production counter from the reduced samples.
- **R14 — Financial and vesting evidence.** Certificate-level price and contribution are historical evidence, not current Settings share prices. No automatic update to legal rights, liquidation multiples, voting, conversion ratios, authorized shares or present-day signers. Preserve vesting text; numerical vesting events, complex schedules and rights need separately approved support. Do not label all positions fully vested merely because examples are.

### Files, reconciliation and execution

- **R15 — Dates and formulas.** Normalized templates use real calendar dates `YYYY-MM-DD`, and optional known UTC timestamps use ISO 8601 with `Z`. Reject invalid/ambiguous dates; do not assume a timezone for date-only values. Ledger issue/transfer dates must not exceed the approved cutoff, and a source certificate must exist before it can be transferred. Read Excel dates using the workbook's date system. Do not execute spreadsheet formulas or external links. Cached formula values are secondary reconciliation evidence, flagged if absent or stale; never import formulas as ledger values. Recompute approved controls independently, not using old workbook totals after rows have been removed.
- **R16 — Files.** Link a manifest row by entity type plus stable legacy ID. Require unique document IDs, supported MIME/size, filename, byte size and SHA-256; verify bytes before promotion. Use approved SharePoint-relative references, never signed URLs, local absolute paths or embedded credentials. Retain originals; never regenerate historical PDFs or add current signatures. No file bytes were supplied with these Excel samples. Existing 10 MB profile-upload limits are not automatic approval for every historical file type.
- **R17 — Reconcile like with like.** Compare counts, per-holder/class balances, certificate statuses, transfers/allocations and documents for the identical population, class definition and cutoff. Separate issued, outstanding and fully diluted definitions. A sampled holder total is not a company total. Conflicting sources produce blocking exceptions with evidence, not an automatic preference.
- **R18 — Idempotency and review.** Fingerprint originals, retain mapping version and row provenance, and compare stable legacy IDs/content across runs. Same-file retries and changed-file repeats must not duplicate records; changed content becomes an explicit conflict/update proposal. All blocking errors must be resolved and warnings accepted before a staged run can be committed. A name typed into an Excel approval column is not authorization.
- **R19 — Historical side effects.** Approved imports write historical records through an import-specific path, with complete atomic ledger promotion and separately tracked/resumable SharePoint verification. They must not create live issuance/transfer requests, send email or synthesize signatures. Incomplete runs are not usable live ledgers. Keep legacy summaries clearly labeled in centralized activity, shareholder history and Transfer History.
- **R20 — Hosting and permissions.** Real source files, staging, processing, production reads/writes and reports run in approved Azure/Microsoft hosting. SharePoint stores originals/reports. Replit development is synthetic-only. Any user already signed into the Azure application may import; no separate role, group or permission assignment is needed.
- **R21 — Reset and future use.** Initial reset is a separately approved Azure-only operation after exact schema verification, write pause and recovery evidence. No reset code is part of this review. Do not drop the shared database. Future imports are available to signed-in Azure app users and remain add-only, with an optional IT pause control; updates require separate review and explicit approval. No workbook-driven deletion.
- **R22 — Safe outputs.** Export error/review sheets as literal text, including strings beginning with `=`, `+`, `-`, `@`, tabs or carriage returns; do not allow formula injection. Receipts contain counts and protected IDs, not sensitive values. Retain complete originals only within approved Microsoft storage.

It belongs in the same build, not a second project. The initial migration mode and future add-only mode must be separate from the reset operation.

## Artifacts and regeneration

Run from the repository root:

```text
python scripts/legacy_import_review/build_review.py
python -m unittest discover -s scripts/legacy_import_review -p 'test_*.py'
```

Outputs are retained under `generated-artifacts/legacy-import-review/` (ignored by Git/deployment):

- `Legacy_Import_Design_Review.html` — standalone shareable review document.
- `Legacy_Import_Mapping_Review.xlsx` — source inventory, every source-header disposition, field mappings, rules, findings and decision register.
- `Legacy_Import_Templates_DRAFT.xlsx` — blank proposed templates, instructions and field definitions.
- `Legacy_Import_Synthetic_Example.xlsx` — separate, entirely synthetic linked example; not an approved import.

`source-assessment.json` contains only workbook structures, fingerprints, counts and aggregate numeric diagnostics, not source personal rows. The read-only profiling script is optional design tooling for approved anonymized examples; it is not called by the generator or tests. No part of these scripts is an application import endpoint.
